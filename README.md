# Simple Chat Application Using Redis

A backend-only chat room application built with Java, Spring Boot, and Redis. It provides REST APIs to create chat rooms, join rooms, send messages, and retrieve recent chat history. Redis is used for room metadata, participant membership, message history, and Pub/Sub events.

This project was created for a backend assignment. It exposes REST APIs only; no frontend UI is included.

## Tech Stack

- Java: 21
- Spring Boot: 4.1.2
- Spring Web: REST API layer
- Spring Data Redis: Redis data access and Pub/Sub integration
- Redis: Primary data store and message broker
- Maven: Build and dependency management
- JUnit 5 + Mockito: Service-layer unit tests
- Springdoc OpenAPI: Swagger UI and API documentation
- Jakarta Bean Validation:Request validation
- Lombok: Boilerplate reduction

## Features

- Create chat rooms with unique room names.
- Join an existing chat room as a participant.
- Send messages only after joining the room.
- Store chat history in Redis Lists and retrieve the latest N messages.
- Use Redis Pub/Sub to publish messages to room-specific channels.
- Handle duplicate room names, invalid room IDs, non-member messaging, and invalid request fields.
- Keep controller, service, repository, mapper, and Pub/Sub responsibilities separated.

## Redis Data Model

| Purpose | Redis structure | Key / channel | Stored data |
|---|---|---|---|
| Room metadata | Hash | `chatrooms` | Room ID mapped to room metadata/value |
| Participants | Set | `chatroom:{roomId}:participants` | Unique participant names |
| Chat history | List | `chatroom:{roomId}:messages` | `ChatMessage` objects, appended in chronological order |
| Live message events | Pub/Sub | `room_channel:{roomId}` | Newly published chat messages |

Messages contain the following fields:

```json
{
  "participant": "guest_user",
  "message": "Hello, everyone!",
  "timestamp": "2026-11-16T10:00:00Z"
}
```

The timestamp is generated by the backend when a message is mapped from the incoming request.

## Prerequisites

- JDK 21

## Run Locally

### 1. Start Redis

Using Docker:

```bash
docker run --name redis-chat -p 6379:6379 -d redis:7-alpine
```

Check that the Redis container is running:

```bash
docker ps
```

If the container already exists but is stopped:

```bash
docker start redis-chat
```

### 2. Configure the Redis connection

By default, Spring Boot connects to Redis at `localhost:6379`.

For a hosted Redis instance, provide the connection details through environment variables:

```text
SPRING_DATA_REDIS_HOST=<your-redis-host>
SPRING_DATA_REDIS_PORT=<your-redis-port>
SPRING_DATA_REDIS_PASSWORD=<your-redis-password>
```

Do not commit real Redis credentials to GitHub.

### 3. Run the application

From the project root:

**Windows PowerShell:**

```powershell
.\mvnw.cmd spring-boot:run
```

**Linux / macOS:**

```bash
chmod +x mvnw
./mvnw spring-boot:run
```

The application starts at:

```text
http://localhost:8080
```

Alternatively, open the project in IntelliJ IDEA and run `RedischatApplication.java`.

## REST API Reference

Base path:

```text
/api/chatapp/chatrooms
```

### 1. Create a chat room

**POST** `/api/chatapp/chatrooms`

Request:

```json
{
  "roomName": "general"
}
```

Success response:

```json
{
  "message": "Chat room 'general' created successfully.",
  "roomId": "general",
  "status": "success"
}
```

Room names are unique. Creating an existing room returns an error response.

### 2. Join a chat room

**POST** `/api/chatapp/chatrooms/{roomId}/join`

Example URL:

```text
POST /api/chatapp/chatrooms/general/join
```

Request:

```json
{
  "participant": "guest_user"
}
```

Success response:

```json
{
  "message": "User 'guest_user' joined chat room 'general'.",
  "status": "success"
}
```

The room must exist before a participant can join it.

### 3. Send a message

**POST** `/api/chatapp/chatrooms/{roomId}/messages`

Example URL:

```text
POST /api/chatapp/chatrooms/general/messages
```

Request:

```json
{
  "participant": "guest_user",
  "message": "Hello, everyone!"
}
```

Success response:

```json
{
  "message": "Message sent successfully.",
  "status": "success"
}
```

The room must exist, and the participant must already be a member of that room. On success, the message is saved to the room's Redis List and published to its Redis Pub/Sub channel.

### 4. Retrieve chat history

**GET** `/api/chatapp/chatrooms/{roomId}/messages?limit=10`

Example URL:

```text
GET /api/chatapp/chatrooms/general/messages?limit=10
```

Success response:

```json
{
  "messages": [
    {
      "participant": "guest_user",
      "message": "Hello, everyone!",
      "timestamp": "2026-11-16T10:00:00Z"
    },
    {
      "participant": "another_user",
      "message": "Hi, guest_user!",
      "timestamp": "2026-11-16T10:01:00Z"
    }
  ]
}
```

The API returns the latest `limit` messages in chronological order. If `limit` is omitted, the controller uses `50`. If `limit` is zero or negative, the service falls back to `10`.

## Error Handling

The application validates request fields and handles expected chat errors, including:

- Creating a room that already exists.
- Joining a room that does not exist.
- Sending a message to a room that does not exist.
- Sending a message as a participant who has not joined the room.
- Blank room names, participant names, or message text.

Expected chat and validation errors are returned as HTTP 400 responses. Unexpected exceptions are handled by the global exception handler.

## Redis Pub/Sub Notes

The publisher sends each new message to `room_channel:{roomId}`. The Spring Redis message listener subscribes to the `room_channel:*` pattern, receives published events, and writes the received channel and message payload to the application log.

This demonstrates room-specific Redis Pub/Sub publishing and backend subscription. The current assignment implementation does **not** include a WebSocket/SSE endpoint or a frontend client connection layer, so the listener log is not the same as pushing messages to connected browser/mobile users.

To observe the Redis broadcast independently, open two terminals and run this command in each:

```bash
redis-cli PSUBSCRIBE "room_channel:*"
```

Then send a message to an existing room using Postman. Both Redis CLI subscribers should receive the published message. The application listener should also log the event.

## Run Tests

Run the test suite from the project root:

**Windows PowerShell:**

```powershell
.\mvnw.cmd test
```

**Linux / macOS:**

```bash
chmod +x mvnw
./mvnw test
```

The service-layer test class contains 10 unit test cases covering:

1. Successful room creation.
2. Duplicate room rejection.
3. Successful room joining.
4. Joining a non-existent room.
5. Successful message saving and publishing.
6. Successful message-history retrieval.
7. Rejection of a non-member sending a message.
8. Rejection of sending a message to a non-existent room.
9. Zero history limit falling back to 10.
10. Negative history limit falling back to 10.

A separate Spring Boot context-load test is also included.

These are unit/context tests. The Redis Pub/Sub behavior should additionally be checked with a running Redis instance using the manual subscriber steps above.

```text
src/test/java/   # JUnit 5 and Mockito tests
```

## Scope and Notes

- This is a backend assignment project; no UI is included.
- Redis persistence (RDB snapshots/AOF) is not configured by this application. Configure persistence on the Redis server if durability is required.
- Chat room deletion is not implemented because it is an optional assignment extension.
- Redis Pub/Sub is fire-and-forget; messages are persisted separately in the Redis List for later history retrieval.
