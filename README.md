A backend-only chat room application built with Java 21, Spring Boot, and Redis. It provides REST APIs to create chat rooms, join rooms, send messages, and retrieve recent chat history.

The implementation follows the assignment scope: REST APIs, Redis as the primary data store and message broker, and Postman-based testing. No frontend UI or WebSocket/SSE endpoint is included.

## Tech stack

## Features

- Create chat rooms with unique room names.
- Join existing chat rooms.
- Allow only joined participants to send messages.
- Store chat history in Redis and retrieve the latest messages.
- Publish each new message to a room-specific Redis Pub/Sub channel.
- Validate room names, participant names, and message text.
- Handle duplicate rooms, missing rooms, non-member messaging, malformed JSON, invalid request parameters, and unknown endpoints.

## Redis data model

| Purpose | Redis structure | Key / channel | Value |
|---|---|---|---|
| Room metadata | Hash | `chatrooms` | Hash field is the room ID; value is JSON containing `roomId`, `roomName`, and `createdAt` |
| Participants | Set | `chatroom:{roomId}:participants` | Unique participant names |
| Message history | List | `chatroom:{roomId}:messages` | Typed `ChatMessage` JSON objects, appended in chronological order |
| Live message events | Pub/Sub | `room_channel:{roomId}` | Newly published `ChatMessage` JSON |

`StringRedisTemplate` is used for room metadata and participant data. A typed `RedisTemplate<String, ChatMessage>` with `JacksonJsonRedisSerializer<ChatMessage>` is used for message history and Pub/Sub publishing. The typed serializer writes the message fields without polymorphic `@class` metadata.

A chat message has this shape:

```json
{
  "participant": "guest_user",
  "message": "Hello, everyone!",
  "timestamp": "2026-11-17T10:00:00Z"
}
```

The timestamp is generated by the backend when the request is mapped to a `ChatMessage`.

## Run locally

### 1. Start Redis

If Redis is not already running locally, start a Redis container:

```powershell
docker run -d --name redis-chat -p 6379:6379 redis:7-alpine
```

Check the container:

```powershell
docker ps
```

If the container already exists but is stopped:

```powershell
docker start redis-chat
```

The application uses `localhost:6379` by default. If your Redis container has a different name, use that name in the `docker exec` commands below.

### 2. Configure Redis (when not using localhost)

Set these environment variables for a hosted or non-default Redis instance:

```text
SPRING_DATA_REDIS_HOST=<redis-host>
SPRING_DATA_REDIS_PORT=<redis-port>
SPRING_DATA_REDIS_USERNAME=<redis-username>
SPRING_DATA_REDIS_PASSWORD=<redis-password>
```

Set the username only when the Redis provider requires one. Do not commit real Redis credentials to GitHub.

### 3. Run the application

From the directory containing `pom.xml`:

**Windows PowerShell**

```powershell
.\mvnw.cmd spring-boot:run
```

**Linux / macOS**

```bash
chmod +x mvnw
./mvnw spring-boot:run
```

Alternatively, open the project in IntelliJ IDEA and run `RedischatApplication.java`.

The API starts on port `8080` by default:

```text
http://localhost:8080
```

## REST API reference

**Live Base URL:** `https://redis-chat-backend-production.up.railway.app`
**Local Base URL:** `http://localhost:8080`

Base path:

```text
/api/chatapp/chatrooms
```

### 1. Create a chat room

**POST** `/api/chatapp/chatrooms`

Request:

```json
{
  "roomName": "general"
}
```

Success status: `201 Created`

Response:

```json
{
  "message": "Chat room 'general' created successfully.",
  "roomId": "general",
  "status": "success"
}
```

Room names must be non-blank, contain no more than 50 characters, and use letters, digits, underscores, or hyphens. Room names are unique.

### 2. Join a chat room

**POST** `/api/chatapp/chatrooms/{roomId}/join`

Example Local URL:

```text
POST http://localhost:8080/api/chatapp/chatrooms/general/join
```

Request:

```json
{
  "participant": "guest_user"
}
```

Success status: `200 OK`

Response:

```json
{
  "message": "User 'guest_user' joined chat room 'general'.",
  "status": "success"
}
```

The room must exist before a participant can join it. Participant names must be non-blank and no longer than 50 characters.

### 3. Send a message

**POST** `/api/chatapp/chatrooms/{roomId}/messages`

Example Local URL:

```text
POST http://localhost:8080/api/chatapp/chatrooms/general/messages
```

Request:

```json
{
  "participant": "guest_user",
  "message": "Hello, everyone!"
}
```

Success status: `200 OK`

Response:

```json
{
  "message": "Message sent successfully.",
  "status": "success"
}
```

The room must exist and the participant must already be a member of that room. Message text must be non-blank and no longer than 500 characters. On success, the message is appended to the Redis List and published to `room_channel:{roomId}`.

### 4. Retrieve chat history

**GET** `/api/chatapp/chatrooms/{roomId}/messages?limit=10`

Example Local URL:

```text
GET http://localhost:8080/api/chatapp/chatrooms/general/messages?limit=10
```

Success status: `200 OK`

Response:

```json
{
  "messages": [
    {
      "participant": "guest_user",
      "message": "Hello, everyone!",
      "timestamp": "2026-11-17T10:00:00Z"
    },
    {
      "participant": "another_user",
      "message": "Hi, guest_user!",
      "timestamp": "2026-11-17T10:01:00Z"
    }
  ]
}
```

- If `limit` is omitted, the controller uses `10`.
- If `limit` is zero or negative, the service falls back to `10`.
- If `limit` is greater than `100`, the service caps it at `100`.
- Messages are returned in chronological order among the selected latest messages.

## Error handling

Error responses use this shape:

```json
{
  "status": "error",
  "message": "Room does not exist!"
}
```

Current status mapping:

| Scenario | HTTP status |
|---|---:|
| Duplicate room name | `409 Conflict` |
| Room does not exist | `404 Not Found` |
| Participant has not joined the room | `403 Forbidden` |
| Request validation failure | `400 Bad Request` |
| Malformed JSON body | `400 Bad Request` |
| Invalid request parameter type (for example, `limit=abc`) | `400 Bad Request` |
| Unknown endpoint | `404 Not Found` |
| Unexpected server error | `500 Internal Server Error` |

Unexpected server errors return a generic response rather than exposing internal exception details.

## Redis Pub/Sub testing

The application publishes new messages to `room_channel:{roomId}`. Its Redis message listener subscribes to the `room_channel:*` pattern and logs received channel and message payloads. The assignment implementation does not include a WebSocket/SSE endpoint or a frontend connection layer; the listener log is a backend subscription demonstration, not a browser/mobile push channel.

To verify broadcast delivery, open two PowerShell terminals and run the following command in each. Replace `my-redis` with your Redis container name if different:

```powershell
docker exec -it my-redis redis-cli PSUBSCRIBE "room_channel:*"
```

Then send a message to an existing room through the REST API using Postman. Both Redis CLI subscribers should receive the published message, and the Spring Boot application log should show the subscriber event.

To inspect stored messages for a room:

```powershell
docker exec -it my-redis redis-cli LRANGE "chatroom:general:messages" 0 -1
```


**Linux / macOS**

```bash
./mvnw clean test
```

The service-layer test class contains 10 JUnit 5 / Mockito tests covering:

1. Successful room creation.
2. Duplicate room rejection.
3. Successful room joining.
4. Joining a non-existent room.
5. Successful message saving and publishing.
6. Successful message-history retrieval.
7. Rejection of a non-member sending a message.

## Scope and limitations

- This is a backend-only assignment; no UI is included.
- Redis Pub/Sub is fire-and-forget. Message history is persisted separately in the Redis List.
- The subscriber currently logs received events; connected browser/mobile delivery via WebSocket or SSE is not implemented.
- Redis persistence (RDB/AOF) is not configured by the application; it can be configured on the Redis server if required.
- Chat room deletion is not implemented because it is optional in the assignment.
